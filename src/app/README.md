# app

`app` is the bootstrap of the Qabz service. The type `App` owns every long-lived dependency: the logger, the Postgres database, the Redis cache, the metrics endpoint and the optional tracer. Entry points (for example `cmd/start-app`) build an `App` and run it. They hold no wiring of their own.

`App` depends only on small interfaces (`Logger`, `Database`, `Cache`, `Metrics`, `Tracer`), never on the concrete Postgres, Redis, zap or Prometheus types. Only `Config` is a concrete type. You make an `App` with `Builder`. `Build()` fails if the logger, database, cache or metrics is missing. `NewDefaultBuilder` is the one place that creates the real implementations from `Config`, which is read from a YAML file.

`Start` pings the database and the cache, prints their status in the log (host, port and database name only, never a password), and starts the metrics endpoint. If a step fails, it releases what it opened. `Stop` closes everything in reverse order and is safe to call twice. `Run` starts, waits for the context to end, then stops. Tests build an `App` with fakes and need no running server.

After the config reloader, `Start` starts the gRPC server (`entry/grpc`, address `server.grpc.addr`, default `:8082`) and then the HTTP gateway (`entry/http`, address `server.http.addr`, default `:8080`). The gateway serves the grpc-gateway routes and dials the local gRPC server, so each HTTP call runs through the real gRPC stack. `GET /v1/greeting` returns `{"message":"Hello"}` to ping the service.

`GET /v1/services` returns the service list (the bill types) from the `services` table of the `bill` database, in the same form as `bill`: the rows of the `Accept-Language` language (the raw header value; `fa-IR` when it is missing), by the `order` column, with `serviceId` from `service.id`. `NewDefaultBuilder` wires the handler (`entry/grpc`) to a `billtype.ServiceCatalog` (`core/billtype`) over `postgres.ServiceRepository`. The catalog keeps each language in memory for `config.CacheServicesTTL` (60s, a const) and never caches a failed read. A failed read gives gRPC `Internal` (HTTP 500) with no detail and writes one error log line with the cause (`services: list failed`); a call that the client canceled is not logged. Each call adds 1 to `qabz_services_cache_total{result="hit"|"miss"|"error"}`. One difference from `bill`: `inquiry` is sent as stored, not always `true` (`docs/this_vs_bill.md`, item 1).

`POST /v1/mybill` (gRPC `MyBills.Insert`) saves a bill for the user of the JWT in the `bills` table of the `bill` database, with the rules of `bill`. `NewDefaultBuilder` wires the handler (`entry/grpc/mybills.go`) to a `savedbill.Store` (`core/savedbill`) over `postgres.SavedBillRepository`. The store checks the request by type (bill ID check digit, mobile and landline numbers after the 0/98 normalization in `common/helpers`), sets the default name and, for `mobile`, the `mci` operator. A bill that the user already has (an enabled row with the same `bill_id` or the same inquiry ID in `data`, of any type) is not saved again: the answer has the existing id. The answer echoes the request, as `bill` does. An invalid request gives gRPC `InvalidArgument` (HTTP 400) and writes no log line; a failed write gives `Internal` (HTTP 500) with no detail and one error log line (`mybill: insert failed`); a call with no user (only with `debug.auth.disable` and an empty `debug.auth.mock_user_id`) gives `PermissionDenied`. Each saved bill adds 1 to `qabz_mybill_insert_total{result="created"|"existing"}`. The differences from `bill` are items 5 to 8 of `docs/this_vs_bill.md`.

`GET /v1/mybill` (gRPC `MyBills.GetAll`) returns the saved bills of the user of the JWT, as `bill` does: the enabled rows of the user from `bills`, newest first (`created_at DESC`, then `id DESC`), and `serviceId` = `service.id`. The handler maps each row with the rules of `bill`: for `tel` and `mobile`, `billId` and `phone` are the stored phone (`data`, or `bill_id` when `data` is empty), and a later row with a phone already in the list is left out; for `gas`, `participateCode` is `data`; a type that is not in the proto enum is sent as `gas`. `operator` and `isPined` come from `json_data`, read on the hot path with fastjson the way `bill`'s `encoding/json` reads it (keys match without case, so `operator` is read; `isPined` is not `IsPinned`). A user with no bills gets `"data": []`. A failed read, or a `json_data` value of the wrong type, gives `Internal` (HTTP 500) and one error log line (`mybill: list failed`); a call with no user gives `PermissionDenied`. The differences from `bill` are items 6, 9 and 10 of `docs/this_vs_bill.md`.

`DELETE /v1/mybill/{id}` (gRPC `MyBills.Delete`) deletes a saved bill of the user of the JWT as `bill` does. The row stays: the store (`savedbill.Store.Delete`) checks the id with `uuid.Parse` of `github.com/google/uuid` v1.6.0 (bill's check and version: upper case, `{...}`, 32 hex digits and `urn:uuid:` are accepted), and the repository runs `UPDATE bills SET status = 'disable' WHERE id = <id> AND user_id = <user> RETURNING type` with the id as the client sent it (cast from text, so Postgres reads it); `RETURNING type` only reads the bill type for the metric. Only `status` changes, so `GET /v1/mybill` no longer lists the bill. An unknown id, a bill of another user and a bill that is already disabled change nothing and still succeed. Success is HTTP 200 with `message` = `عملیات با موفقیت انجام شد` ("the operation was done successfully", task 019b; bill sends its `invalid_parameter_error` text on success). Every failure gets bill's answer, gRPC `Unknown` (HTTP 500) with bill's `invalid_parameter_error` text `خطای داخلی رخ داده است`: an id that does not parse, an empty id, a call with no user, and a database error (also an id that Postgres rejects, such as `urn:uuid:...`). Only the database error writes a log line (`mybill: delete failed`, with the cause); the client errors write none, although their code is `Unknown` (conventions § 10, operator decision of task 019). Each successful delete adds 1 to `qabz_mybill_delete_total{type,result}`: `result` is `found` (a bill of the user has the id) or `not_found`; `type` is `bills.type` of that bill, or `unknown` for `not_found` and for a NULL type. The differences from `bill` are items 11 (no log line for a call with no user) and 12 (the success text) of `docs/this_vs_bill.md`.

**Providers (task 020).** `provider.ProvidersService` (`provider/selector.go`) is the in-memory sorted list of the `providers` table of the `bill` database, and the only way to read providers (conventions § 13). After the config reloader and before the gRPC server, `Start` loads the rows once, synchronously, through `postgres.ProviderRepository` (raw SQL, every row). A failed first load does not stop the start: it writes one error line (`providers: load failed; keeping the last list`), the list stays empty and `PickProvider` gives `provider.ErrNoProvider`. A reload routine then loads the rows every `providers.general.load_interval` (default `1m`, at least `1s`; hot-reloadable as `providers_load_interval` in `app_hot_configs`: a change applies at once (operator decision 9): `config.Holder.Changed()` wakes the routine, and when the effective value (after the `1s` minimum) changed it stops the wait in progress and runs the next load at (start of the last load + new interval), at once when that time is past; the same effective value restarts nothing, and a load in progress is not interrupted; a lower hot value is used as `1s` with one warn line per new low value). Each load replaces the whole list (the database wins): in each (`bill_type`, `action`) group the order is `tmp_priority` (a runtime key, equal to `priority` after each load) ascending, then `id` ascending. Each load has a fixed timeout of 10 s (`loadTimeout` in `provider/selector.go`, not a config key): a slower load fails with `context deadline exceeded`, is counted as `error` and keeps the last list. A failed later load keeps the last good list and writes one error line; a load that `Stop` cancels at shutdown is not a failure (no error line, no count), and neither is a first load that fails with `context.Canceled` because the `App.Start` context itself is canceled (the start is being aborted; `Start` returns as before). A load canceled for another reason, or one that times out, is logged and counted. After each load, each group whose order (ids and status) changed gets one debug line `providers: group order` with `bill_type`, `action`, `order` (`id:tmp_priority:status,...`) and `pick`. `PickProvider(billType, action)` returns the first enabled (`status = 'enable'`) provider of the group from memory, with no other logic and no allocation; `MoveUp` / `MoveDown` (the group's `tmp_priority` values become 0..n-1, then the two neighbors swap) and `Enable` / `Disable` change the runtime list until the next load. Every method is safe for concurrent use: readers read one atomic snapshot and never wait; writers run one at a time and store a new snapshot. Metrics: `qabz_providers_loads_total{result="ok"|"error"}`, `qabz_providers_load_duration_ms`, `qabz_providers_last_load_success_timestamp_ms`, `qabz_providers_changes_total{change,result}` and `qabz_providers_active_count` (no labels: the enabled providers in all groups of the current list, set after each good load and each `Enable` / `Disable` that changed the list; a failed load keeps the value). No endpoint reads providers yet. The difference from `bill` (sorted pick, no Redis cache) is item 13 of `docs/this_vs_bill.md`.

`POST /v1/water/inquiry` (gRPC `Water.Inquiry`, task 021) inquires a water bill. `NewDefaultBuilder` wires the handler (`entry/grpc/water.go`) to `inquiry.Service` (`core/inquiry`) over `postgres.InquiryRepository` (`bill_inquiries`, `bill_inquiry_requests`), `ProvidersService` and a `provider.Registry`. The flow: pick the provider of (`water`, `inquiry`) with `PickProvider`; take its adapter from the registry; look in `bill_inquiries` for rows of the same `inquiry_id` (the `billId`) and provider that are younger than `caching.water` (default `1h`, `0` turns it off; read at start, not hot-reloadable), not a copy (`is_cached = false`) and not paid; a hit answers with no provider call and saves copies for the user (`is_cached = true`); a miss writes the `bill_inquiry_requests` row (`initial`), calls the adapter, sets the status and the provider trace ID of the row, and saves each inquiry. The registry holds the Qabzino adapter (`provider/qabzino`, gRPC `haf80.api.qabzino.Inquiry/BillInquiry` at `providers.qabzino.grpc_address`, each call limited by `providers.qabzino.timeout`). **Provider mocks:** with `mode: dev` and `debug.mocks.qabzino.enable: true`, `provider.NewMock` wraps the adapter: `Inquiry` answers a fixed answer (`return_type: success`: pay ID `2500012345`, 25 000 000 rials, deadline `2030-01-01`) or `provider.ErrProviderDown` (`return_type: error`) and never calls the backend; one warn line at start says that the mock is on (conventions § 15). Answers: `InvalidArgument` for an invalid request (no log line); `Unavailable` (HTTP 503) when no provider is enabled, the call fails or the picked provider has no adapter (one error log line each); `FailedPrecondition` (HTTP 400) with the provider message when the provider has no inquiry (no log line); `Internal` for any other failure (one error log line); `PermissionDenied` for a call with no user. With metrics on, each inquiry adds 1 to `qabz_inquiries_total{bill_type,provider,result}` and each provider call adds 1 to `qabz_provider_calls_total{provider,action,result}` and one sample to `qabz_provider_call_duration_ms{provider,action}`. The differences from `bill` are items 14 to 22 of `docs/this_vs_bill.md`.

`POST /v1/electricity/inquiry` (gRPC `Electricity.Inquiry`, task 022) inquires an electricity bill with its details. It uses the same `inquiry.Service` as water: `NewDefaultBuilder` builds the flow once (`newInquiryFlow`, which also registers the three inquiry metrics once) and gives it to both handlers (`newWater`, `newElectricity`; `entry/grpc/electricity.go`). The flow is the flow of water with the bill type `electricity`: the provider of (`electricity`, `inquiry`), the cache TTL `caching.electricity` (default `1h`, `0` turns it off; read at start), the `tid` prefix 2. The registry also holds the Tavanir adapter (`provider/tavanir`, gRPC `haf80.api.tavanir.InternalInquiryService/BillInquiry` at `providers.tavanir.grpc_address`, each call limited by `providers.tavanir.timeout`; `newProviderRegistry` adds each adapter with `registerAdapter`). **Details:** the adapter returns them in `InquiryResponse.Details` (`provider.ElectricityDetails`); the flow saves them with each inquiry and `postgres.InquiryRepository` writes them to `bill_inquiries.extra_data` as one JSON object (`inquiry_details.go`: bill's keys `city` and `region`, and `phase`, `company_name`, `tariff_type`, `customer_type`, `serial_number`, `service_address`, `service_post_code`, `customer_name`) and reads them back with fastjson (a hot path, conventions § 1), so a hit answers with the same details as the provider call. **Mock:** with `mode: dev` and `debug.mocks.tavanir.enable: true` the adapter answers a fixed answer (`return_type: success`: pay ID `1800012345`, 18 000 000 rials, deadline `2030-01-01` and all details, the `Mock...` constants of `provider/tavanir`) or `provider.ErrProviderDown` (`return_type: error`). The answers of every failure are those of water (`answerInquiryError`), with the log prefix `electricity:`; the metrics are the same three with `bill_type="electricity"` and `provider="tavanir"`. `POST /v1/electricity/inquiry/document` is not written yet (`Unimplemented`). The differences from `bill` are items 23 to 25 of `docs/this_vs_bill.md`.

Every gRPC call, and so every gateway route, is measured first (`entry/grpc/requests.go`, metrics in `common/monitoring/prometheus/requests.go`): it records its time in milliseconds in the histogram `qabz_request_duration_ms{path,code}` (buckets 5 to 10000 ms; durations are in milliseconds per conventions § 9). The histogram's `_count` series is the request counter (for example `rate(qabz_request_duration_ms_count[5m])`); there is no separate counter metric. `path` is the gRPC method (for example `/haf80.api.bill.Service/Greeting`), never the raw URL, and `code` is the gRPC code name (`OK`, `PermissionDenied`, `Internal`, ...). The interceptor runs before the auth check, so a rejected call is counted. An unknown HTTP route ends in the gateway (404) and is not counted.

**Prometheus switch.** `metrics.prometheus.enabled` (default `true`) is the switch of Implementation_Plan Step 5. With `false`, `prometheus.New` returns a disabled server: `NewDefaultBuilder` creates and registers no metric (requests, auth, services cache, mybill inserts and deletes, providers, inquiries and provider calls), nothing is recorded, the metrics endpoint does not listen, and `Start` logs `metrics disabled` in place of `metrics started`.

Every gRPC call, and so every gateway route, goes through the JWT auth check (`entry/grpc/auth.go`, verifier in `common/auth`). A call without a valid `Authorization: Bearer <token>` gets gRPC `PermissionDenied` (HTTP 403) with the message "unauthenticated". The check accepts only HMAC tokens (`HS256`, `HS384`, `HS512`) signed with the secret that the auth service shares (`auth.secrets.hmac`, never printed) and needs `exp`, `sub` (a UUID), `mobile`, `non_otp` (not `guest`) and an `aud` string (any value: it is not compared, as in `bill`; it goes into the claims). Every other `alg` (`none`, RSA, ECDSA) is rejected. Qabz only verifies tokens. Each rejection adds 1 to `qabz_auth_rejected_total{reason}` and writes no log line. `debug.auth.disable: true` turns the check off for development and logs one warning at start; then `debug.auth.mock_user_id` (a lower-case UUID, default empty) is the user of every call, so handlers that need a user (My Bills) work without a token, and with it empty a call has no user; a mode other than `dev` fully removes the `debug` section (task 020c), so in `stage` and `prod` the check is always on, and a missing key keeps the check on. With the check on, `NewDefaultBuilder` fails when the secret is missing. The metrics endpoint is outside the check. `Stop` stops the metrics endpoint, the gateway, the gRPC server, then the providers reload routine and the config reloader. A failed `Start` stops only the parts that started.

Before the metrics endpoint starts, `Start` runs the SQL migrations (`database.migration.on_start`, default true; many containers can start together, because the migrator takes a Postgres advisory lock) and starts the optional config reloader. A `Config` field with the tag `hot_reload:"true"` is read again from the table `app_hot_configs` every `hot_reload_interval`. `App.Config()` returns a copy of the current settings, so do not keep it.

The config key `mode` (`dev`, `stage` or `prod`) is required: without it, or with another value, `config.Boot` panics and neither the App nor a command starts. Now it changes only the development commands.

**Development database (`devdb`).** `go run . devdb --config=../config.yml seed` (in `src/`) creates every table of the `bill` service database that does not exist yet, as bill's code makes them (`system/postgres/devdb/schema.sql`), inserts the seed rows of `services` (5) and `providers` (45) whose `id` does not exist, and moves the two id sequences past the largest id. `devdb ... unseed` deletes those seed rows by `id`; the tables stay. Both run in one transaction, a second run changes nothing, and they print the row counts. They run only with `mode: dev`: with `stage` or `prod` they exit 1 before they connect. The `bill` tables are not qabz migrations (qabz does not own them).

```go
cfg, _ := config.Boot(os.Args[1:])  // --config=path/to/config.yml is required; a bad file panics
                                    // start from config.yml.example: cp config.yml.example config.yml

b, err := app.NewDefaultBuilder(ctx, cfg)   // real zap, Postgres, Redis, Prometheus
if err != nil { return err }

a, err := b.Build()                 // or app.NewBuilder().WithLogger(fake)... in a test
if err != nil { return err }

return a.Run(ctx)                   // blocks until ctx is cancelled, then stops
```

Qabzino (task 030). `newProviderRegistry` registers the direct adapter `provider/qabzino` under the name `qabzino`: it calls Ayantech over HTTPS with `providers.qabzino.token`, `water_bill_endpoint` and `timeout`. `providers.qabzino.enabled` (default `false`) is the switch: `false` writes one warn line at start, every Qabzino inquiry fails as provider down with no call to Ayantech, and `debug.mocks.qabzino` does not apply (the switch wins; the mock needs `enabled: true`). The gRPC adapter is package `provider/qabzinoproxy` (QabzinoProxy); the App does not build it. No test or check sends a call to Ayantech (each call is charged): tests use a local `httptest` server.
