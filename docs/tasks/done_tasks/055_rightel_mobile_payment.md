# 055_rightel_mobile_payment — Rightel mobile bill order and payment

Status: done (2026-11-16; the operator QA on stage waits for the operator)

## Description

Pay a Rightel mobile bill. Read tasks 044 (landline), 045 (status worker) and 048 (water) and `docs/this_vs_bill.md` items 38 to 47 first: the order flow (`core/order`, `billTypes`), the payment step (`order.Payments`, `PayRoutes` in `src/app/defaults.go`), the Parsian adapter `Pay` and the shared status worker already exist. The design step reads `../bill` (commit `ff98e25`) again and lists the steps for the operator before any code, as task 048 did.

**What `bill` does (read 2026-11-16):** `Phone.NewOrderV2` maps rightel `midTerm` to the bill type `mobilemidtermRightel` (only the mid term; the token keys are those of task 054; `bill` has a commented-out block that disabled Rightel payment because of the provider). The payment gateway (`gateway/payment/mobile_rightel.go`) has `ParsianRightelMobile` (`TopBill/Pay`, the inquiry type of the request) and `EWaysRightelMobile` (NATS). The "bill already paid" window is `parsian.settlementInquiryRightelMobile` (EWays: `ewaysV2.settlementInquiryRightelMobile`). No settlement. Seed order providers: row 37 `eways2` (**enabled**), row 500 `parsian` (disabled).

Today `POST /v1/mobile/order` answers `Unimplemented` for `rightel` (task 039); the Rightel inquiry (task 037, through Qabzino) already exists and only Qabzino may answer it.

**Open points for the design step:** (1) Qabz has no EWays adapter and no NATS, and the seed enables EWays for Rightel: confirm that Qabz pays Rightel through Parsian only (row 500 enabled in the Qabz database) as for the other types; (2) the `parsianproxy.Pay` bill type `mobilemidtermRightel`; (3) `settlement_inquiry_rightel_mobile` (`0s`, not read); (4) the Postman request.

## Definition of Done

- `POST /v1/mobile/order` for the operator `rightel` (`midTerm`) creates the order and the token as `bill`; a Rightel `fullTerm` request answers as `bill` (the table has no entry).
- ParsianProxy pays `mobilemidtermRightel`; `OrderComplete` answers `success`, `failed` and `pending`.
- `OrderComplete` itself gives the final status of a normal payment. An order that it leaves `pending` or `in-progress` (a Parsian timeout, a short downtime) is finalized later by the Parsian status worker (task 045) with no code change; a test with a `pending` Rightel order proves it.
- `docs/this_vs_bill.md` has an item for each difference from `bill`, with a `@todo` at the code; `system.html`, the config examples, the Postman collection, the CHANGELOG and the QA scenario in `OPEN_TASKS.md` are updated in the same commit.
- Unit tests with stubs and live tests on the run database (conventions § 14), the metrics of conventions § 12, the spans of conventions § 17. Build, vet and tests (with `-race`) pass; each changed package is at 70.0 % or more.
- Feature ON (Rule 15): a run in dev mode with the mock, with the evidence analyzed: the order, `OrderComplete` for `success`, `failed` and `pending`, the Kafka report of the status worker for a pending order, and the metrics. The operator QA on stage stays open in `OPEN_TASKS.md`.

## Design (implementer, 2026-11-16; waits for the operator approval)

Read on 2026-11-16 from `bill` commit `ff98e25` (not run) and from the Qabz source at `7df5c26`. Q1 and Q2 need an operator answer; every other item follows `bill` and tasks 048, 052, 053 and 054. Each difference from `bill` that a client, the payment service or the database can see gets an item (or an extension of an item) in `docs/this_vs_bill.md` and a `@todo` at the code.

**Summary.** In `bill` the Rightel order is the MCI order with one bill type: `phoneBillTypeMapper` maps rightel `midTerm` to `mobilemidtermRightel` (`BillTypeInquiryType` `midterm`) and has no `fullTerm`. `NewOrder` has no direct price rule (only `Irancell`) and no provider fee (`AvailableBillTypes` has only the Karashop bill types), so the price is the raw inquiry when `billId` and `payId` are numeric, else the inquiry of `mobilemidtermRightel` (Qabzino `QabzinoRightelMobile`). The payment gateway maps the bill type to `EWaysRightelMobile` (NATS) and `ParsianRightelMobile` (`TopBill/Pay`, the fields of `ParsianMCIMobile`). No settlement. `NewOrderV2` has a commented-out block that refused Rightel ("disabled by the provider"); `service/myBill/newOrder.go` (the saved-bill order, not in Qabz) still refuses Rightel for users that are not on a white list.

### The order (`POST /v1/mobile/order`, operator `rightel`)

- **D1. The entry.** `orderOperators` (`src/entry/grpc/phone_order.go`) gets the entry of `rightel`: `midTerm` → `mobilemidtermRightel` (the existing `provider.BillTypeMobileMidTermRightel`). No `fullTerm` entry, as bill. A `fullTerm` request takes the existing path "a payment term that the operator does not have": HTTP 400 `invalid parameter`, no log line (bill: the bill type is empty, the provider lookup fails, gRPC `Unknown` HTTP 500 `خطای داخلی رخ داده است`). This difference is already in `this_vs_bill.md` item 38; the item gets the Rightel sentence. No operator answers HTTP 501 after this task. The rest of `Phone.NewOrder` does not change (the 98 form, the request check, `orders.option` `rightel`, the token with `order.PhoneData`, `service` `rightel`).
- **D2. The payment provider — Q1.** Seed rows of (`mobilemidtermRightel`, `order`): row 37 `eways2` priority 10 **enable**, row 500 `parsian` priority 9 `disable`. Qabz has no NATS and no EWays adapter (as tasks 052 and 053). Proposal: **Parsian only** (only `parsian` gets the `PayRoutes` entry) and the dev seed row 500 changes to `enable` (priority 9: Parsian is the pick before row 37). An enabled `eways2` row that the pick takes (the Parsian row off) gives the case 2 `failed` answer of task 048 (an order provider with no payment route). The stage and prod rows are the operator's database change (follow-up).
- **D3. The flow (`core/order`, one new `billTypes` entry).** `mobilemidtermRightel`: `{inquiryType: midterm}` (no `inquiryBillType`: the inquiry bill type is the order bill type, as bill; so no item 42 difference here).
  1. The order provider of (`mobilemidtermRightel`, `order`).
  2. The "bill already paid" check (D4).
  3. The price: the raw inquiry when `billId` and `payId` are numeric; else (or when it fails) the inquiry of `mobilemidtermRightel` with the phone (task 037: only Qabzino may answer, seed row 34 `enable`), and the mid-term inquiry of the answer is the price.
  4. A price of 0 is `FailedPrecondition` with bill's text; the provider fee is 0; the fee is `fee.Resolver` (default 9000; bill's `MobileMidtermRightelFee` 9000 in `GetBillMetaData` is not read by the fee, as bill); the `orders` row `initial`.
- **D4. The "bill already paid" window — Q2.** `providers.internal.parsian.settlement_inquiry_rightel_mobile` exists and is not read; the Qabz example says `"0s"`, the task text says `0s`. **bill's example value is `360h`** (`config.example.yaml`: `parsian.settlementInquiryRightelMobile: 360h`; MCI is `0`). Proposal: read it for `mobilemidtermRightel` of `parsian`, default `360h` (bill's example, as tel, water, electricity and gas), and change the example to `"360h"`. A negative value is rejected. 0 is "the orders of any time" (the shared `LastStatus`, as MCI).
- **D5. Saved inquiries of a Rightel order.** No new key: bill reads `caching.paidMobile` for (`mobilemidtermRightel`, `order`), so Qabz reads `caching.paid_mobile` (default `1h`) for it too. It applies only when the price comes from the provider inquiry. The comments of the key (config, example) name both bill types.
- **D6. The token `data` map.** `order.PhoneData` (the keys of bill's `NewOrderV2`). The metadata (bill: `case MOBILEMIDTERMRIGHTEL`): `about` `قبض موبایل` (`AboutIconMobileMidterm`), `aboutIcon` `https://public.780.ir/dl/Operator/logOrhightel2.svg` (`RightelIcon`), `feeDescription` `کارمزد`.

### The payment (`OrderComplete`, sync)

- **D7. The payment route.** `PayRoutes` of `parsian` gets `mobilemidtermRightel`; `parsianproxy.Pay` pays it (`payBillTypes`; bill: `ParsianRightelMobile`, the same fields as `ParsianMCIMobile`: `provider_order_id` from the RRN, `bill_type` `mobilemidtermRightel`, `inquiry_type` `midterm`, `amount` the base price, `inquiry_id` the phone). The Parsian mock answers with no change. `TestPayDown` now uses another bill type that Parsian does not pay (`irancell` and `""` stay).
- **D8. After a success.** bill's `updateCache` side effects (the `is_paid` of the `bill_inquiries` rows, `last_order_date` of the saved bills), as the other bill types. No settlement (`settleRoutes` has only `tel` and `telmidterm`).
- **D9. The `failed` answer.** No change: cases 1 to 3 of task 048 are in the shared code. `mobilemidtermRightel` is added to `TestCompleteFailedOrderAnswersFailed`. Task 048 D12 applies to Rightel too.
