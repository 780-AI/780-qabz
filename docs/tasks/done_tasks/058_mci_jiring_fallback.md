# 058_mci_jiring_fallback — MCI payment fallback to the next provider (Jiring Switch)

Status: done (2026-11-16; the operator QA on stage waits for the operator)

## Description

Task 054 pays the MCI bill types `mobile` and `mobilemidterm` through Parsian only. This task adds the fallback: when Parsian is out of service for sure, `OrderComplete` pays through the next enabled provider row of (bill type, `order`). Today that is Jiring Switch (seed rows 30 and 29, priority 10; Parsian has 9). Read task 054 (the section "D2 revised", D2a to D2f, and the operator answers) first. `bill` has no payment fallback.

**Operator rules (2026-11-16):**
- **No fallback after a timeout.** A timeout (or any call whose status is not known) stays `pending`, as today; the Parsian status worker finalizes it. Only a call that did not reach Parsian for sure (the switch off, no address, a refused connection, gRPC `Unavailable` before the call) goes to the next provider.
- **No hard-coded provider order.** The order of the providers comes only from (1) the operator, who changes the `providers` rows in the database, and (2) the provider selector and the switcher of the future circuit breaker. The code does not name Jiring Switch as the fallback; it takes the next enabled row with a payment route.
- The dev seed rows 29 and 30 (`jiring-switch`, `order`) change to `enable` in this task (task 054 enables row 48).

## Definition of Done

- A sure Parsian "out of service" on `OrderComplete` of `mobile` or `mobilemidterm` saves a new `in-progress` row with the next provider (the same RRN) and pays through it; a timeout stays `pending` with no second call. With no next enabled provider, the answer is that of today.
- The Jiring Switch adapter has `Pay` (`InternalInquiryService/PayBill`, bill's `JiringSwitchMCIMobile` fields) and `Status` (`GetStatus`), with their mocks (conventions § 15).
- A Jiring Switch status worker (`providers.internal.jiring_switch.get_status.*`) on the shared status worker of task 050; the pending-order query takes the newest row of each order over all providers before it filters by the provider, so no worker writes over the row of another provider.
- The "already paid" windows have `jiring-switch` for `mobile` and `mobilemidterm` (bill: 0).
- `docs/this_vs_bill.md` has an item for the fallback and for the query change, with a `@todo` at the code; `system.html`, the config examples, the CHANGELOG and the QA scenario in `OPEN_TASKS.md` are updated in the same commit.
- Unit and live tests (conventions § 14), the metrics of conventions § 12 and the spans of conventions § 17 show both providers. Build, vet and tests (with `-race`) pass; each changed package is at 70.0 % or more.
- Feature ON (Rule 15): the Parsian switch off and the Jiring Switch mock on: an order paid by the fallback; a Parsian timeout that stays `pending`; the Jiring Switch worker finalizes a pending Jiring order.

## Design (implementer, 2026-11-16; approved by the operator: "Approve design")

Read on 2026-11-16 from `bill` commit `ff98e25` (`gateway/payment/mobile_mci.go` `JiringSwitchMCIMobile`, `gateway/paymentInquiry/jiringSwitch.go`, `pkg/cronTask/jiringSwitchGetStatus.go`) and from the Qabz source at `303d74e`. bill has no payment fallback.

- **D1. A sure "not sent": `provider.ErrNotSent`.** It always comes with `provider.ErrProviderDown` (the code that tests `ErrProviderDown` does not change). An adapter returns it only when: the switch is off; there is no address; gRPC answers `Unavailable` and the request headers never went to a connection. A stats handler on the gRPC client marks the call at `stats.OutHeader` (grpc-go v1.85.0 sends it only after the headers frame is queued on a live connection). Every other error (a timeout also when the headers did not go out, a cancel, `Unavailable` after the headers, any status of the server) is `ErrProviderDown` only: the order stays `pending`, as today (operator rule: no fallback after a timeout).
- **D2. The fallback (`order.Payments.Complete`, step 6), for every bill type.** After a sure "not sent", the step reads `Group(bill type, order)` of `ProvidersService` (priority, then id), skips the providers it already tried, and takes the first enabled row whose provider has a payment route for the bill type and an adapter. It saves a new `in-progress` row with that provider (`provider_id`, `provider_name`, the same RRN, the error of the last call as the message), pays, and saves the answer. A second sure "not sent" goes on to the next row while one is defined. No next row: the answer of today (`pending`, 500, the error text; operator). No provider name and no bill type list in the code. With the seed, only the MCI groups have a second provider with a payment route.
- **D3. The Jiring Switch adapter.** `Pay` (`InternalInquiryService/PayBill`, bill's fields: `provider_order_id` = the day of the year in Tehran and the RRN as text, `inquiry_type`, `amount` the base price, `inquiry_id` the phone) for `mobile` and `mobilemidterm`; `Status` (`GetStatus`, `purchase_type` `bill`; `tid` is the trace ID); the errors of D1. Mocks: `debug.mocks.jiring_switch.pay_return_type` and `status_return_type` (conventions § 15). `PayRoutes` of `jiring-switch`: `mobile`, `mobilemidterm`.
- **D4. The Jiring Switch status worker** on the shared worker of task 050: the new switch `providers.internal.jiring_switch.get_status.enabled` (default `false`); the `get_status.*` keys get the defaults and the checks of the Parsian worker (name `jiring-switch-getstatus`; a name different from the other workers).
- **D5. The pending query.** `pendingIDsSQL` takes the newest row of each order over all providers in the window, then filters by the provider (only the orders with a row of the provider in the window are read). The worker also skips an order whose newest row has another provider.
- **D6. "Already paid" windows:** `jiring-switch` `mobile` and `mobilemidterm` `0` (bill).
- **D7. Seed:** rows 29 and 30 `enable` (a database seeded before keeps `disable`).
- **D8. Metrics and spans:** `qabz_order_payment_fallback_total{bill_type,from,to}`; the provider calls on `qabz_provider_pay_duration_ms` by provider; `order.Payments.Complete` gets `provider.first` when the provider changed; the Jiring worker on the shared worker metrics (`cron` `jiring-switch-getstatus`).
- **D9. Docs:** `this_vs_bill.md` (a new item for the fallback; item 43 for the query), conventions § 13 (a named exception, operator 2026-11-16), `system.html`, the config examples, the app README, the CHANGELOG, the manifest and the QA scenario in `OPEN_TASKS.md`.

**Operator answers on the design (2026-11-16):** the fallback is for every bill type, only when a next provider row is defined ("most situations are limited to only one provider, so the error is inevitable"); with no next provider the answer is `pending`, as today; Q1 (a) a timeout before the headers stays `pending`; Q2 (a) a next provider that is not reached goes to the one after it. Conventions § 13 conflict (one request, one provider): the operator chose "Add an exception" (a named exception in § 13, same commit).
