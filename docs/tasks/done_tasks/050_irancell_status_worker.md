# 050_irancell_status_worker — the Irancell status worker

Status: done (2026-11-16; the operator QA waits for the operator)

## Description

A status worker for the orders of the provider `irancell`, as the Parsian status worker of task 045. Read task 045 and `docs/this_vs_bill.md` item 43 first. Needs task 045 (the shared worker runner, `reconcile.StatusWorker`, the Kafka reporter) and task 047 (tracing).

**bill's worker** (`../bill`): `pkg/cronTask/irancellGetStatus.go` (`IrancellGetStatusTask`, config `irancell.getStatus.*`) runs the shared `InquiryCron` (`service/billPaymentInquiry/dto.go`) with the name `irancell`. The status call is `gateway/paymentInquiry/irancell.go`: gRPC `InternalService/GetStatus` of the `irancell` service with `OrderId` and `PurchaseType: "charge"`. A gRPC error is `pending`; else the status is `response.Status`, the provider trace ID is `response.Tid` and the message is `response.Message`. Only `success` and `failed` are final.

**Reuse, no copy.** `reconcile.StatusWorker` (`src/core/reconcile/status.go`) takes the provider as an option. The Irancell worker is a second instance with `Provider: irancellproxy.Name`, wired in `src/app/crons.go` next to the Parsian worker. The new code is:
- `Adapter.Status` in `src/provider/irancellproxy/irancellproxy.go` (now `ErrNotSupported`): the `GetStatus` call above, with the timeout `providers.internal.irancell.timeout`. A failed call is `provider.ErrProviderDown`.
- The Irancell mock answers `success`, `failed` and `pending` for the status (conventions § 15).
- Config `providers.internal.irancell.get_status.*` with the same keys as the Parsian worker (`enabled`, default `false`; `name`; `cron_time`; `start`; `end`; `chunk`; `lock_time`; `reverse_deadline`; `sync_operations`), in `config.yml.example` and `config.yml` (§ 8). bill's example config has no Irancell worker values, so the design step asks the operator for the defaults.

**Defects of bill's worker that this task MUST fix.** For each one, the design step checks if task 045 already fixed it in the shared code. If yes, a test proves it for the Irancell worker. If no, the fix goes into the shared code, so the Parsian worker gets it too (the design names that change to the operator).
1. **Skipped orders in the pages.** bill reads pages with `OFFSET` and adds `chunk` each time, but an order that the run made final leaves the result set, so other pending orders move back past the offset and that run does not check them. The fix: no pending order of the window is skipped in a run (for example a keyset page on `created_at, order_id`, or a snapshot of the IDs at the start of the run). A test with more pending orders than `chunk`, and some of them made final, proves it.
2. **Kafka before the database.** bill reports on Kafka and saves after. A failed save after a good report leaves the payment service with the final status and the order with `pending`, and the next run reports again. The fix: the design gives a way with no lost status and no wrong state (for example the save first and the report after, with a retry of a failed report), and asks the operator if the payment service accepts a second report of the same order.
3. **Two different windows.** bill reads the newest row of the last 48 h (`GetOrderByIDWithIntervals`) but the final save locks the newest row of the last 24 h (`NewOrderWithFinalStatus`). An order from 24 h to 48 h old fails at the save each time. The fix: one window for the read and the save (`order.LatestWindow`).
4. **No timeout and no stop.** bill asks with `context.Background()`. The call uses the context of the run and the adapter timeout (task 045 has this; a test proves it for Irancell).
5. **Errors with no log line.** bill skips most errors with `continue` and writes nothing.

**Every error writes a log line (operator, 2026-11-15).** A failed page read, a failed order read (now counted with no line: `ResultReadError`), a failed or timed-out status call, an unknown status text from Irancell, a failed report, a failed save, a lost lock, a failed release and a panic each write one error line with the worker name, the order ID (when there is one) and the error. This changes conventions § 10 ("counted, no line") for the read error: the design step names the change and, if it goes into the shared worker, the Parsian worker writes the same lines.

**A metric of the statuses fixed in each run (operator, 2026-11-15).** A Prometheus metric gives the number of orders that the run moved to a final status (`success`, `failed`, and the late saves), for each run and each worker. Name and type are a design step (conventions §§ 9, 12), for example a histogram `qabz_cron_orders_fixed` with the label `cron`, observed once at the end of each run (also 0), next to the counters that exist (`qabz_cron_runs_total`, `qabz_cron_duration_ms`, `qabz_cron_orders_processed_total`, `qabz_provider_calls_total` with action `status`).

**Tracing (conventions § 17).** The root span of each tick, a child span for each order, and the `GetStatus` call, Kafka and Postgres spans under it.

**Open point for the design step.** Qabz has no Irancell payment yet (`Adapter.Pay` is `ErrNotSupported`), so the pending Irancell orders come only from bill in a shared database. The design step confirms the source of the orders with the operator and that bill's own Irancell worker and this worker do not run on the same orders at the same time.

### Corrections of this task file

- **C1. Defect 1 is smaller in Qabz than the task says.** The pending query filters the rows on the window before it takes the newest row (task 045 C6). A final row that the worker saves is newer than `now-start`, so with `start > 0` the order stays in the list and the `OFFSET` pages do not move. A skip still occurs when (a) `start` is `0` (the saved row is in the window), (b) another path writes a final row in the window during the run (`OrderComplete`), or (c) the old end of the window moves during a long run (orders leave the front of the list). The fix (D4) covers the three cases; the test uses case (a) and case (b).
- **C2. Defects 4 and 5 are partly fixed by task 045.** Each call has the run context and the adapter timeout (defect 4). The runner writes one line for a failed page read and a lost lock (`cron: run failed`), a failed lock (`cron: lock failed`), a failed release and a panic, each with the worker name. Open: a failed order read, a failed status call and an unknown status text write no line (D7).
- **C3. The local `config.yml` has the Irancell worker values.** `providers.internal.irancell.get_status`: `cron_time` 15m, `name` `irancell-get-status`, `start` 30m, `end` 48h, `chunk` 100, `lock_time` 30m, `reverse_deadline` 10h, `sync_operations` 30s / 3ms / 3ms (the Parsian values, but `end` is 48h). D2 proposes them as the defaults, as task 045 D2 did.

### The worker

- **D1. A second instance of the shared worker.** `reconcile.StatusWorker` with `Provider: irancellproxy.Name` and the `get_status` keys of Irancell, wired in `newCrons` (`src/app/crons.go`) next to the Parsian worker, on the same runner (one Redis lock for each worker name: `qabz:crons_irancell-get-status_lock1`). The Kafka producer and the reporter are made when one of the two status workers is on (today: only Parsian). `kafka.brokers` and the write subject must not be empty when one of them is on.
- **D2. Config `providers.internal.irancell.get_status.*` (decision: the defaults).** New key `enabled` (default `false`: no worker, the behavior of today). The other keys become read and are checked at start when `enabled` is true, as Parsian: `name` not empty, `cron_time` and `chunk` positive, `0 <= start < end`, `end` not greater than 48h (the read window, D5), `reverse_deadline` 0 or more. `every` and `is_lockable` stay "not read" (bill has them; Qabz uses `cron_time` and always takes the lock). Proposed defaults: the values of C3.
- **D3. The Irancell adapter `Status`** (`src/provider/irancellproxy/irancellproxy.go`; bill: `IrancellPaymentInquiry`). The call is `InternalService/GetStatus` with `order_id` and `purchase_type` `charge`, with the timeout `providers.internal.irancell.timeout` and the context of the run. `enabled: false`, no address, a gRPC error (a timeout too) and a nil answer return an error that wraps `provider.ErrProviderDown` (the worker counts it `pending`, as bill). Else the answer is `Status` = `status`, `Message` = `message`, `ProviderTraceID` = `tid`, used as they are. The `Client` interface gets `GetStatus`. The gRPC client span exists (task 047, `otelgrpc`).
- **D4. Defect 1: keyset pages (shared code; Parsian gets it too).** `PendingIDs` takes a cursor (the `created_at` of the newest row in the window and the `order_id` of the last order of the page) in place of the offset, and gives `(order_id, created_at)` pairs, ordered by `created_at, order_id`. The query is bill's query with `AND (created_at, order_id) > ($cursor_time, $cursor_id)` on the ranked rows, and `LIMIT` with no `OFFSET`. The key of an order only grows (a newer row), so no order of the window is skipped in a run. A run still reads each order once only. `this_vs_bill.md` item 43 changes.
- **D5. Defect 3: one window (shared code).** `InsertFinal` locks the newest row of the last `order.LatestWindow` (48h), the window of the read, in place of 24h (`lockLatestSQL`). `InsertFinal` is used only by the status worker. An order of 24h to 48h now gets its final status saved; bill fails at the save each time.
- **D6. Defect 2: the order of the report and the save (decision; shared code).** Choose one:
  - **(a, recommended) Save, report, commit.** `InsertFinal` takes the report as a step inside its transaction: lock the newest row (D5), check that it is not final, insert the final row, report on Kafka, then commit. A failed report rolls back, so nothing is saved and the next run asks again (no lost status). A failed lock or insert happens before the report, so nothing is reported (no wrong state). The only gap left: the report is delivered and the commit fails; the next run reports again. Each publish gets the limit `kafka.timeout` (default `5s`, now read), so the row lock is short. This also closes the task 045 follow-up (d) (no limit on each publish).
  - **(b) An outbox column.** Save the final row with a "not reported" mark, report after, and a later run reports the marked rows again. No gap, but a new column in `orders` (a schema change of `database.html`) and a second query in each run.
  - **(c) bill's order, with a retry of the save.** Report, then retry a failed save 3 times. The gap stays when the database is down.

  **Confirmed (operator, 2026-11-16):** the payment service accepts a second report of the same order with the same final status.
- **D7. Every error writes one line (shared code; operator rule of 2026-11-15).** New error lines of the worker, with `name`, `order_id` and `error`: `<provider> status: read failed` (the newest row; now counted with no line), `<provider> status: call failed` (an adapter error or a nil answer; not when the run context is done at the App stop), `<provider> status: unknown status` (a text that is not an order status: not `success`, `failed`, `pending` or `in-progress`; with the text). The lines that exist stay: `report failed`, `save failed`, and the runner lines of C2. A final row that another path wrote between the read and the save (`ErrAlreadyFinal`) is not an error: result `skipped`, one info line `<provider> status: already final`, nothing reported. The Parsian worker writes the same lines. **Conventions § 10 changes:** "a failed step of a worker writes one error line, also when the next run retries it" (the read error was "counted, no line"). A mock `pending` (`provider.ErrProviderDown`, the answer of a timeout) writes the `call failed` line.
- **D8. The metric of fixed statuses (conventions §§ 9, 12).** New histogram `qabz_cron_orders_fixed{cron}`, buckets 0, 1, 5, 10, 25, 50, 100, 250, 500, 1000, 2500. One observation at the end of each run that took the lock, also with 0 and also when the run ends with an error: the count of the orders of the run with the results `success`, `failed` and `late`. A new `StatusOptions.OnRunDone(name string, fixed int)`. The Parsian worker observes it too. The existing counters stay (`qabz_cron_runs_total`, `qabz_cron_duration_ms`, `qabz_cron_orders_processed_total`, `qabz_provider_calls_total{provider="irancell",action="status"}`).
- **D9. The Irancell mock (conventions § 15).** New key `debug.mocks.irancell.status_return_type`: `success`, `failed` or `pending` (`provider.ErrProviderDown`, as the Parsian mock), default `success`. `irancellproxy.MockFixtures` gets `Status` (trace `mock-irancell-0001`). Only in dev mode.
- **D10. Tracing (conventions § 17).** No new span: the root span of the tick, `reconcile.StatusWorker.check` for each order (task 049) and, under it, the `GetStatus` client span, `kafka.Publish` and the Postgres spans. A span-tree test for the Irancell worker.
- **D11. The source of the orders (decision).** Qabz has its own database (`database.postgres.db: qabz`, task 044 D17) and no Irancell payment (`Adapter.Pay` is `ErrNotSupported`, no `PayRoutes` entry). So no Irancell order of Qabz gets `pending` or `in-progress` today, and bill's worker cannot read the Qabz orders. Choose one:

## Implementation notes (implementer, 2026-11-16)

- **I1. `in-progress` is an order status, not an unknown text (D7).** A status text of the provider that is `success`, `failed`, `pending` or `in-progress` writes no line; any other text (also an empty one) writes `<provider> status: unknown status`. The design text first named only three statuses.
- **I2. The builder gate.** `NewDefaultBuilder` built the runner only for the Parsian and the settlement switch; the Irancell switch is added there too (found by `TestDefaultBuilderCrons`), with the info line `irancell status worker off (...)` when it is off.
- **I3. The shared config check.** The checks of a status worker are one function for both workers (`validateStatusWorker`); the 48 h limit of `end` applies only to Irancell (D2); the Kafka checks (with `kafka.timeout` positive) run when one of the two workers is on; the two worker names must differ while both are on (the lock key and the metric label).
- **I4. `order.ErrAlreadyFinal`.** The sentinel moved to `core/order`, so the worker can tell a final row of another path (D7: skipped, no report) from a failed save; `postgres.ErrAlreadyFinal` is the same value.
- **I5. Code-review fixes (the `code-reviewer` agent, NOT READY with two defects):** (a) `qabz_cron_orders_fixed` added to the list of `TestDefaultBuilderMetricsSwitch` / `TestMetricsOffRegistersNothing` (conventions § 12); (b) the index reads of `status_test.go` and `crons_test.go` guarded (conventions § 4). Note N2 applied: a report or a save that fails because the App stop canceled the run writes no error line (counted), as the § 10 text says (`TestStopWritesNoReportOrSaveLine`; the positive control without the check fails). Notes N1, N3 and N4 need no change. The reviewer also saw the known flaky `TestInquiryOneCallFails` (`provider/karashop`, task 039 follow-up (d), not part of this change).
