# 052_electricity_payment — Electricity bill order and payment

Status: done (2026-11-16; the operator QA on stage waits for the operator)

## Description

Pay an electricity bill, as the water bill (task 048). Read tasks 044 (landline), 045 (status worker) and 048 (water) and `docs/this_vs_bill.md` items 38 to 47 first: the order flow (`core/order`, `billTypes`), the payment step (`order.Payments`, `PayRoutes` in `src/app/defaults.go`), the Parsian adapter `Pay` and the shared status worker already exist. The design step reads `../bill` (commit `ff98e25`) again and lists the steps for the operator before any code, as task 048 did.

**What `bill` does (read 2026-11-16):** `Electricity.NewOrder` / `NewOrderV2` (`controller/electricity/newOrder.go`) call `controller.CreateNewOrder` with `entity.ELECTRICITY`; the V2 token `data` keys are `payId`, `type`, `billId`, `payAmount`, `rawAmount`, `about`, `aboutIcon`, `invoicePayID`, `invoiceBillID`, `receiptPayID`, `receiptBillID` and, with a fee, `feeAmount` and `feeDescription` (V1 has `payId`, `type`, `billId`). The payment gateway (`gateway/payment/electricity.go`) has two providers: `ParsianElectricity` (`TopBill/Pay`, `inquiry_type` `regular`, `provider_order_id` from the RRN) and `EWaysElectricity` (NATS). The "bill already paid" window is `parsian.settlementInquiryElectricity`. No settlement (the confirm-payment map has only `tel` and `telmidterm`). Seed order providers: row 47 `parsian` (enabled), row 17 `eways2` (disabled).

**Open points for the design step:** (1) the same as water: the route is Parsian only (Qabz has no NATS and no EWays adapter); confirm with the operator; (2) the price rules (raw inquiry first or the Tavanir inquiry; `bill`'s `AvailableBillTypes`; the saved-inquiry key, for example `caching.paid_electricity`); (3) the key `providers.internal.parsian.settlement_inquiry_electricity` is `0s` and not read: its default for Qabz; (4) the Postman request.

## Definition of Done

- `POST /v2/electricity/order` creates the order and the signed token as `bill`; `POST /v1/electricity/order` stays `Unimplemented` as for water.
- ParsianProxy pays `electricity` (`PayRoutes` of `parsian`); `OrderComplete` answers `success`, `failed` (every failed case, task 048 D10 and D11) and `pending` as for water.
- `OrderComplete` itself gives the final status of a normal payment. An order that it leaves `pending` or `in-progress` (a Parsian timeout, a short downtime) is finalized later by the Parsian status worker (task 045) with no code change; a test with a `pending` electricity order proves it.
- `docs/this_vs_bill.md` has an item for each difference from `bill`, with a `@todo` at the code; `system.html`, the config examples, the Postman collection, the CHANGELOG and the QA scenario in `OPEN_TASKS.md` are updated in the same commit.
- Unit tests with stubs and live tests on the run database (conventions § 14), the metrics of conventions § 12, the spans of conventions § 17. Build, vet and tests (with `-race`) pass; each changed package is at 70.0 % or more.
- Feature ON (Rule 15): a run in dev mode with the mock, with the evidence analyzed: the order, `OrderComplete` for `success`, `failed` and `pending`, the Kafka report of the status worker for a pending order, and the metrics. The operator QA on stage stays open in `OPEN_TASKS.md`.

## Design (implementer, 2026-11-16; operator approval 2026-11-16: "Approve, D2 Parsian, D7 (a)")

Read on 2026-11-16 from `bill` commit `ff98e25` (not run) and from the Qabz source at `053e369`. Items marked **(decision)** need an operator choice; every other item follows `bill` or the water payment (task 048). Each difference from `bill` that a client, the payment service or the database can see gets an item in `docs/this_vs_bill.md` and a `@todo` at the code.

**Summary.** In `bill` the electricity order and payment are the water order and payment with other texts: the same `controller.CreateNewOrder`, no provider fee (`AvailableBillTypes` is only Karashop `tel`/`telmidterm`/`telephone`), no settlement, the inquiry type `regular`, `ParsianElectricity` with the fields of `ParsianWater`. So task 052 adds entries to the shared code of task 048; it adds no new flow.

### The order (`POST /v2/electricity/order`)

- **D1. The entry.** `Electricity.NewOrderV2` (`NewOrderBillPayRequest` → `NewOrderResponse`; the proto has it), with the steps of `Water.NewOrderV2`: the request check (`billId` or `payId`; else HTTP 400 with no log line, `this_vs_bill.md` item 38 is extended), no user HTTP 403, the inquiry ID (`participateCode`, else `billId`; bill: `SetInquiryID`), `order.Service.Create`, the token. `POST /v1/electricity/order` stays `Unimplemented`, as water. The helper `waterInquiryID` becomes a shared `orderInquiryID` (one copy, not two).
- **D2. The route: Parsian only (decision; approved).** `bill` has two order providers for electricity: `ParsianElectricity` (seed row 47, `enable`) and `EWaysElectricity` (NATS, seed row 17, `disable`). Qabz has no NATS and no EWays adapter, as for water. Recommended: Parsian only; an enabled `eways2` row gives the answer of a provider with no payment route (the case 2 `failed` answer of task 048). Confirm, or name another route.
- **D3. The flow (`core/order`, a new `billTypes` entry `electricity`: `{inquiryType: regular}`, the same as `water`).**
  1. The order provider of (`electricity`, `order`): seed row 47, `parsian`.
  2. The "bill already paid" check (D4).
  3. The price: the raw inquiry when `billId` and `payId` are numeric (bill: `shouldInquiryWithPayID`, as water); else (or when it fails) the provider inquiry of `electricity` with the inquiry type `regular` (`bill`: `BillTypeInquiryType[ELECTRICITY]`), with saved inquiries for `caching.paid_electricity` (D5). **Different from water:** the electricity inquiry provider of the seed is `tavanir` (row 2, `enable`), which has a Qabz adapter (task 034), so this path gives a real price. Note: `POST /v1/electricity/inquiry` reads only `billId` (task 022); the order reads the raw inquiry first, as `bill`.
  4. A price of 0 is `FailedPrecondition` with bill's text; the provider fee is 0; the fee is `fee.Resolver` (default 9000; `bill`'s `ElectricityFee` is also 9000); the `orders` row `initial`.
- **D4. The "bill already paid" window.** `providers.internal.parsian.settlement_inquiry_electricity` exists, is `0s` and is not read. It gets the default `360h` (`bill`'s example value) and is read, as `settlement_inquiry_water` in task 048 D5. The config check rejects a negative value. The `config.yml.example` value changes from `"0s"` to `"360h"`.
- **D5. Saved inquiries for an electricity order.** A new key `caching.paid_electricity`, default `72h` (`bill`: `caching.paidElectricity: 72h`), as `caching.paid_water`. It applies only when the price comes from the provider inquiry.
- **D6. The token `data` map.** The keys of `bill`'s `Electricity.NewOrderV2`, the same as water: `payId`, `type` (`electricity`), `billId`, `payAmount`, `rawAmount`, `about`, `aboutIcon`, `invoicePayID`, `invoiceBillID`, `receiptPayID`, `receiptBillID`, and, with a fee, `feeAmount` and `feeDescription`. `order.WaterData` becomes a shared function for both bill types (the body is the same). The icon is `https://public.780.ir/dl/Operator/Bargh.svg`; the fee description is `کارمزد`.
- **D7. The `about` text (decision; approved: (a)).** `bill`'s `AboutIconElectricity` is `" قبض برق"`, with a space at the start (the other bill types have none).
  - **(a, recommended)** Copy it with the space: the token bytes are those of `bill`, so the payment service and the client see what they see now.
  - **(b)** Remove the space (`قبض برق`), with a `this_vs_bill.md` item.

### The payment (`OrderComplete`, sync)

- **D8. The payment route.** `PayRoutes` of `parsian` gets `electricity`; `parsianproxy.Pay` pays `electricity` (`payBillTypes`; `bill`: `ParsianElectricity`, the same fields as `ParsianWater`: `inquiry_type` `regular`, `provider_order_id` from the RRN, `amount` the base price, `inquiry_id` `orders.data`). The Parsian mock answers `electricity` with no change.
- **D9. After a success.** The side effects of `bill`'s `updateCache`: `is_paid` of the `bill_inquiries` rows and `last_order_date` of the saved bills of the bill ID and `electricity`. No settlement: `settleRoutes` has no `electricity` entry (`bill`: the confirm-payment map has only `tel` and `telmidterm`).
- **D10. The `failed` answer.** No change: the cases 1 to 3 of task 048 (D10, D11) are in the shared code and apply to `electricity`. Tests prove each case for an electricity order. Task 048 D12 (the payment service reads a gRPC error as `failed`) stays open; it applies to electricity too.

### The Parsian status worker (async)

- **D11. No code change.** The worker reads the `pending` and `in-progress` orders by provider only, so an electricity order of `parsian` is in its window; it asks `TopBill/OrderInquiry` with `bill_type` `electricity`; the report message has the same bytes as a water order. A live test finalizes a `pending` electricity order (`success` and `failed`) and checks the Kafka report.

Docs in the same commit: `config.yml.example`, `system.html`, `this_vs_bill.md` (item 38 extended; an item for D7 only if (b)), the Postman item Electricity / Order V2 (with a default `electricity_payId` that passes the raw check), `src/app/README.md`, `folder_structure.md` (new files), the CHANGELOG, the manifest and the QA scenario in `OPEN_TASKS.md`.
