# 056_irancell_payment — Irancell mobile bill payment (OrderComplete)

Status: done (2026-11-16; the operator QA on stage waits for the operator)

## Description

Pay an Irancell order that exists since task 039. The order endpoint (`POST /v1/mobile/order`, bill type `irancell`, order provider row 26 `irancell`) is done; the payment step is not: `irancellproxy.Adapter.Pay` returns `provider.ErrNotSupported` and `PayRoutes` has no `irancell` entry. Read tasks 044 (landline), 045 (status worker) and 048 (water) and `docs/this_vs_bill.md` items 38 to 47 first: the order flow (`core/order`, `billTypes`), the payment step (`order.Payments`, `PayRoutes` in `src/app/defaults.go`), the Parsian adapter `Pay` and the shared status worker already exist. The design step reads `../bill` (commit `ff98e25`) again and lists the steps for the operator before any code, as task 048 did.

**What `bill` does (read 2026-11-16):** the payment gateway (`gateway/payment/mobile_irancell.go`, `IrancellMobile`) sends the whole `PaymentRequest` as a **NATS request** (`orderbus.Nats.Request`) to the subject `irancell.natsSubject` (`irancell-bill`) and reads a `PaymentResponse` back; a failed request is a `pending` answer. It does not call the irancell gRPC service (the proto `pb/proto/irancell/internalService.proto` has no payment RPC for a bill; `GetCharge` and `OrderOffer` are other products). The status of the order is read later by `InternalService/GetStatus` (task 050, done). No settlement.

**Open points for the design step (decision for the operator, the first one blocks the rest):** (1) how Qabz sends the payment to the irancell service: a NATS client in Qabz (a new dependency and the keys `providers.internal.irancell.nats_subject` and a NATS address) that keeps `bill`'s message, or a payment RPC that the irancell service must add (a change of its proto in the `pb` submodule, conventions § 6); (2) the message bytes of `PaymentRequest` / `PaymentResponse` (a differential test against `bill`'s structs, as the Kafka message of task 045); (3) the "pending" rule for a timeout; (4) the mock (conventions § 15); (5) once the payment exists, the Irancell status worker of task 050 has work: the deploy config `get_status.enabled` is part of this task's follow-ups.

## Definition of Done

- The payment route of `irancell` exists and `Adapter.Pay` pays an Irancell order with the transport that the operator chose in the design step; the request and the answer match `bill` (or the new RPC) byte for byte, checked by a test.
- `OrderComplete` answers `success`, `failed` and `pending` for an Irancell order; a timeout is `pending`.
- `OrderComplete` itself gives the final status of a normal payment. An Irancell order that it leaves `pending` or `in-progress` (a timeout, a short downtime) is finalized later by the Irancell status worker (task 050), end to end (a live test and the feature-ON run).
- `docs/this_vs_bill.md` has an item for each difference from `bill`, with a `@todo` at the code; `system.html`, the config examples, the Postman collection, the CHANGELOG and the QA scenario in `OPEN_TASKS.md` are updated in the same commit.
- Unit tests with stubs and live tests on the run database (conventions § 14), the metrics of conventions § 12, the spans of conventions § 17. Build, vet and tests (with `-race`) pass; each changed package is at 70.0 % or more.
- Feature ON (Rule 15): a run in dev mode with the mock, with the evidence analyzed: the order, `OrderComplete` for `success`, `failed` and `pending`, the Kafka report of the status worker for a pending order, and the metrics. The operator QA on stage stays open in `OPEN_TASKS.md`.

## Design (implementer, 2026-11-16; waits for the operator approval)

**Operator decision (2026-11-16):** the transport is NATS, as bill ("Go with NATS"). The irancell service does not change.

Read on 2026-11-16 from `bill` commit `ff98e25` (not run), from the irancell service (`../irancell`, commit `3a18bec`, not run) and from the Qabz source at `b36f0e2`.

**The chain in bill.** `completeOrder` (`service/billPayment/completeOrder.go`) builds a `payment_gateway.PaymentRequest` and calls `IrancellMobile.Execute` (`gateway/payment/mobile_irancell.go`): `orderbus.Nats.Request(ctx, irancell.natsSubject, request, &response)`, a NATS request/reply on a JSON `EncodedConn` (`client/broker/nats_dto.go`, nats.go v1.11.0) with a fixed 30 s limit (`pkg/orderbus/nats.go`). An error (timeout, no connection, a bad answer) is `pending` (code 500, the error text). The irancell service (`app/application_dto.go:453`) reads the subject in the queue group `irancell-bill`; `NatsBillCallback` (`service/bill/dto.go`) decodes `entity.BillRequest`, checks the phone (`^989\d{9}$`, from `inquiry_id`, else `data`), saves its own charge row and calls Irancell (`PayBill`), and answers `entity.ChargeResponse` `{"code","message","tid","status"}`: `success` with code 200, `failed`, `pending`, or (a bad message or a bad phone) code 400 with **no status**. bill keeps `success`, `failed` and `pending` and makes every other status `pending` (`validStatuses`); `ref_id` is `response.ProviderTraceID`, which stays **empty**, because bill's `PaymentResponse` has no JSON tags and no field matches `tid`. bill fails its start when NATS does not connect (`initMessageBroker`).

### The NATS client (`system/nats`, new; the folder of `system.html` "request/reply")

- **D1. The client.** `system/nats.Client` over `github.com/nats-io/nats.go` (the newest release that is at least two weeks old; `go mod tidy && go mod vendor`). Options as bill: the client name `service.name`, the servers, user and password, `allow_reconnect`, `max_reconnect`, `reconnect_wait`, the connect `timeout`, a ping every 60 s. One method `Request(ctx, subject, data []byte) ([]byte, error)` (`nats.Conn.RequestWithContext`; Qabz marshals the bytes itself, so no `EncodedConn`, which nats.go has deprecated). `Close` drains the connection in `App.Stop` after the servers and the workers.
- **D2. The config (new section `nats`, bill's `Nats` keys in snake_case, conventions § 8).** `nats.endpoints` (list, no default: the real values only in `config.yml`), `nats.username` (no default), `nats.password` (a Secret, no default), `nats.auth` (bool, default `false`; bill passes it to `nats.Options.Secure`, that is TLS, not the user and password: Qabz does the same and the comment says so), `nats.allow_reconnect` (default `true`), `nats.max_reconnect` (default `50`), `nats.reconnect_wait` (default `5s`; bill: the number 5 in seconds), `nats.timeout` (default `3s`; bill: 3). bill's `nats.encoder` is not a key: Qabz sends JSON only (this_vs_bill item). Read at start, not hot-reloadable. `providers.internal.irancell.nats_subject` (exists, no default) is now read.
- **D3. When the client exists — Q2.** The client is made only when the irancell adapter needs it: `providers.internal.irancell.enabled: true` and the Irancell mock off. Proposal (a): the App starts also when NATS does not answer (`RetryOnFailedConnect`; one error line `nats: connect failed`, then nats.go connects again in the background); while there is no connection, an Irancell payment is `pending` (the answer of a timeout) and the Irancell status worker finalizes it later. bill stops its start instead. A missing `nats.endpoints` or `nats_subject` with the adapter enabled is one warn line at start and every Irancell payment is `pending` (as a disabled provider).

### The payment (`irancellproxy.Adapter.Pay`)

- **D4. The request message, byte for byte as bill.** A struct with bill's JSON names in bill's order, marshalled with `encoding/json/v2` (`encoding/json` v1 is forbidden, conventions § 1): `{"inquiry_id","bill_id","pay_id","order_id","user_id","dialer","rrn","amount","option","type","InquiryType"}` (`InquiryType` has no tag in bill, so the Go name is the key). Values: the phone (`orders.data`), the bill ID and pay ID of the order (`irancell` when the order had a direct price), the order ID, the user ID, the dialer (empty: the payment service gives none, as bill), the RRN, the base price (rials), the option (`irancell`), the bill type `irancell`, the inquiry type `final_term`. `provider.PaymentRequest` gets the field `Option` (the order step fills it from `orders.option`; the other adapters do not read it). A golden test pins the bytes; the golden value comes from bill's own struct and `encoding/json` v1 in a scratch program outside the repository (as the Kafka message of task 045), and a test also checks the v2 HTML escapes for a value with `<`, `>` and `&` (v1 escapes them; v2 does not unless asked: the encoder is set to escape them as v1).
- **D5. The answer.** Parsed with `fastjson` (a provider answer is a hot path, conventions § 1; the parser comes from a `fastjson.ParserPool`): `code` (number), `message`, `status`, `tid`. `status` is kept as it came (the order step keeps `success`, `failed`, `pending` and makes any other value, also an empty one, `pending`: the code 400 answer of a bad phone is `pending`, as bill). bill's v1 decode matches the keys without case; the irancell service writes them in lower case, so Qabz reads only the lower-case keys (this_vs_bill item). An answer that is not a JSON object is `provider.ErrProviderDown` (bill: the decode error, `pending`). **`tid` — Q1.**
- **D6. Failures.** The switch off, no subject, no client: `ErrProviderDown` with no message sent. A timeout (D7), no connection, no responder (nats.go `ErrNoResponders`), a bad answer: `ErrProviderDown`; the order step saves `pending` with the error text (code 500), as bill. The status worker of task 050 finalizes it.
- **D7. The time limit — Q4.** Proposal (a): a new key `providers.internal.irancell.pay_timeout`, default `30s` (bill's fixed value), positive; `providers.internal.irancell.timeout` stays the limit of the gRPC calls.
- **D8. The route.** `PayRoutes` gets `irancellproxy.Name: {irancell: true}` (the order provider row 26 `irancell`). `SupportsPay` is `irancell` only. No settlement (bill: none for Irancell). No "bill already paid" window (bill has no `irancell` entry in `getNewOrderConflictProviders`; no change since task 039). After a `success` the side effects of the other bill types run (`is_paid`, `last_order_date`).
- **D9. The mock (conventions § 15).** `debug.mocks.irancell.pay_return_type` (`success`, `failed`, `pending`; default `success`) and the fixture `MockFixtures().Pay`: `success` code 200 with bill's success text and `tid` `mock-irancell-0001`; `failed` code 400 with a fixed text; `pending` is `ErrProviderDown`. With the mock on, no NATS client is made.

### Metrics, spans, status worker

- **D10. Metrics (conventions § 12).** The payment is counted by the existing `qabz_order_payment_total{bill_type="irancell",provider="irancell",status}` and `qabz_provider_pay_duration_ms{provider="irancell",status}`. New: `qabz_nats_requests_total{subject,result}` (`ok`, `timeout`, `no_responders`, `no_connection`, `error`), `qabz_nats_request_duration_ms{subject}` (a histogram in ms, conventions § 9), and the gauge `qabz_nats_connected` (1 while connected; set by the connect, disconnect and reconnect handlers, which also write one warn or info line each).
- **D11. Spans (conventions § 17).** A client span `nats.Request` (`messaging.system` `nats`, `messaging.destination.name` = the subject, the result) under `order.Payments.Complete`. No trace header in the NATS message: bill sends none, and the irancell service reads none.
- **D12. The Irancell status worker (task 050).** No code change: it reads the `pending` and `in-progress` orders of the provider `irancell` and asks `GetStatus` with the order ID (the irancell service saves its charge row with the same order ID). A live test with a `pending` Irancell order proves it end to end. The deploy config `providers.internal.irancell.get_status.enabled: true` (stage, prod) becomes a follow-up of this task (task 050 D11 (a)).
