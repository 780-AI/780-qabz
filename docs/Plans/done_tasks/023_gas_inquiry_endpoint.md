# 023_gas_inquiry_endpoint — POST /v1/gas/inquiry and the Qabzino gas adapter

Status: done

## Description

Implement `Gas.Inquiry` (`POST /v1/gas/inquiry`, `pb/proto/qabz/services.proto`). The request is `InquiryBillPayRequest` (`billId`, `payId`, `participateCode`) and the response is `InquiryBillPayResponse` (`price`, `paymentDeadline`, `payId`, `billId`), both in `pb/proto/bill/services.proto`. This task follows tasks 021 (water) and 022 (electricity) and reuses their flow, tables and mock mechanism. It adds the `gas` bill type to the inquiry flow.

**The flow is the same as water (task 021) and electricity (task 022):** pick the provider for (`gas`, `inquiry`) with `ProvidersService.PickProvider` (conventions § 13); look in `bill_inquiries` first (same `inquiry_id`, same `provider_id`, newer than the cache TTL, `is_cached = false`, `is_paid = false`); only on a miss call the provider, write the `bill_inquiry_requests` row, and save the inquiries so the next request within the TTL is answered from the database. Use `core/inquiry` (`Service`), `provider.Registry` and the error mapping of task 021. Do not copy the water flow: extend it for one more bill type. A picked provider with no adapter answers `Unavailable`, as in task 021.

**What is special to this bill type:**
- **`participateCode` is part of the inquiry ID** (`bill`: `controller.SetInquiryID(billId, participateCode)`). The cache lookup uses that inquiry ID, so two participate codes of one bill ID are two cache keys.
- **Raw inquiry** (`bill`: `rawInquiry`): when the request has both `billId` and `payId`, `bill` answers from them with no provider (`raw.Service`). Decide in the design step whether this task includes it; if not, the difference is a `this_vs_bill.md` item.
- **Providers.** In the seed Qabzino gas (id 35) is disabled, Parsian (id 43) is enabled and gas-company (id 99) is disabled. This task adds only the Qabzino gas adapter (the Qabzino adapter already exists). The Parsian and gas-company adapters are NOT in this task: a picked provider with no adapter answers `Unavailable` (task 021 decision 2).

## Design decisions (implementer, 2026-11-11; operator approval "OK, go on. Just make sure requests and responses do not change.")

The Description above was written before task 030. Where it names the gRPC call `haf80.api.qabzino.Inquiry/BillInquiry`, read the direct Qabzino adapter (`provider/qabzino`, HTTPS to Ayantech). The `bill` differences that a client or the database can see are items 28 and 29 of `docs/this_vs_bill.md`, each with a `@todo` at the code.

1. **Requests and responses are not changed (operator).** `Gas.Inquiry` takes `InquiryBillPayRequest` and answers `InquiryBillPayResponse` of `pb/proto/bill/services.proto`, as they are; no proto file is changed. The water and electricity endpoints keep their requests, their answers and their error texts: their tests pass with no change of an expected value, and tests check that a water inquiry still goes to the water endpoint with the water parameters and that the water mock answer is the same.
2. **No type detection.** The handler of each endpoint gives the bill type (`provider.BillTypeGas`). The flow has one table (`billTypes` in `core/inquiry`): the `tid` prefix and the rule of the inquiry ID of each bill type. Water and electricity: a valid bill ID, as before. Gas: not empty (the only rule that `bill` has). A new bill type is a new entry; `Inquire` is not copied.
3. **Inquiry ID = participate code.** `bill`'s request check (`participateCode` or `billId`, and `participateCode` or `payId`; a `billId` that is sent is a valid bill ID) is in the handler (`validGasInquiry`). After it, and after the raw inquiry check, the participate code is never empty, so `SetInquiryID` always gives the participate code. A request with only `billId` is invalid (HTTP 400), as in `bill`. The participate code is the key of the saved inquiries and what the provider gets. No length rule (as in `bill`): a code of more than 15 characters fails at the request row (HTTP 500, one error line).
4. **Raw inquiry: in this task (operator, 2026-11-11).** A request with both `billId` and `payId` is answered from the two IDs, as in `bill` (`raw.Service.Inquiry`): no provider, no saved inquiry, no row. `inquiry.Service.RawInquiry` (`core/inquiry/raw.go`) does the four steps in the order of `bill`: a valid bill ID (`helpers.ValidBillID`), a valid pay ID (`helpers.ValidPayID`), the price from the pay ID (`helpers.PayIDAmount`), the bill type from the bill ID (`helpers.BillTypeOfBillID`); the answer has `price`, `payId` and `billId` and no `paymentDeadline`. The rules are in `common/helpers/payid.go`; they were checked against the `bill` code with a differential test on 400 000 random inputs (no difference; the test file was not kept). The only difference from `bill` is the status of the error answers: `InvalidArgument` (HTTP 400) with `bill`'s three texts, not `Unknown` (HTTP 500) (`this_vs_bill.md` item 28). The first version of this decision said "not in this task"; a review of the working tree found the raw code already written, and the operator kept it.
5. **Meaning of "route through Qabzino" (operator instruction): the same as water.** The Qabzino adapter serves gas; the provider pick (`ProvidersService`) decides which provider answers. The seed is not changed: parsian (id 43) stays the enabled gas provider (no adapter: HTTP 503) and Qabzino gas (id 35) stays disabled, as for water (44 and 36). The feature-ON run enables row 35 with an `UPDATE`.
6. **Qabzino gas adapter.** `POST` to `providers.qabzino.gas_bill_endpoint` (the key exists since task 029; no new provider key) with `{"Identity":{"Token"},"Parameters":{"GasBillID":"","ParticipateCode":<inquiry ID>,"TraceNumber":<UUID>}}`, as the `qabzino` service (`gateway/gas.go`). `G00000`: one inquiry with the amount of the answer (no pay-ID rule; 0 for an empty pay ID, as `QabzinoGas.Execute`), the bill ID of the answer (no fallback), details `city` = `Address`, `kind` = `ConsumptionType`. `GD2038` (no bill to pay): success, one inquiry of amount 0. `GD2031`, `GD2032`, `GD2033`, `GD2037`: failed with bill's text. `GD2036`, `GD2019` and every other code: provider down (item 26). The adapter has one table (`kinds`) for the two bill types; the HTTP code is not copied.
7. **Details.** `provider.Details.Gas` (`city`, `kind`) is saved in `bill_inquiries.extra_data` as `{"city":...,"kind":...}`, the same JSON as `bill`. The client does not get them (the response has no field for them).
8. **Cache TTL.** `caching.gas` (`Config.CachingGas`), default `1h` (as `bill`), `0` turns the cache off, a negative value is rejected, not hot-reloadable (as `caching.water`).
9. **Mock.** `qabzino.MockFixtures` answers a gas request with bill ID `1234567890125`, pay ID `3200012345`, 32 000 000 rials, deadline `2030-01-01`, trace `mock-qabzino-0001`, and the details. `return_type: error` is `provider.ErrProviderDown`. The water mock answer is unchanged.
10. **No enabled provider, errors, metrics, logs.** As water: `Unavailable` (HTTP 503) with the provider-down text and one error line; `FailedPrecondition` (HTTP 400) for a provider with no inquiry; the three metrics with `bill_type="gas"` (no new metric; the Help text names gas); the log lines `gas: no enabled provider for inquiry`, `gas: provider inquiry failed`, `gas: inquiry failed`, `gas: inquiry amount does not fit the price field`.
