# 020b_test_database_isolation — Tests never touch the development database: one random throw-away database for each test run

Status: done

## Description

**Rule (operator, 2026-11-09): what the tests create and drop must never affect the development database.** No test may create, change, drop or reset any object (table, schema, row, migration state) in the database that the App uses in development (`database.postgres.*` in `config.yml`, the compose `qabz` database).

The tests break this rule today. `reset()` in `src/system/postgres/live_test.go:31-37` (the task 003 live tests) runs `DROP TABLE IF EXISTS app_hot_configs, qabz_schema_migrations` in the database that `QABZ_TEST_POSTGRES_DSN` names. When that DSN points to the development database, each full live test run deletes its migration state, and the config reloader then writes an error line at each `hot_reload_interval` until the App runs the migrations again (seen on 2026-11-09 during task 020). The other live tests use `postgrestest` throw-away schemas (`qabz_test_<random>`), but these schemas are still created inside the development database.

**The new model:**
- One throw-away database for each test run: the whole suite of a run, not each test method. It has a random name (for example `qabz_test_<random hex>`), so each run starts from a clean database and two runs at the same time cannot collide.
- The run creates the database on the Postgres server that `QABZ_TEST_POSTGRES_DSN` names, runs the migrations and the seeds that the tests need in it, and drops it at the end of the run (`DROP DATABASE ... WITH (FORCE)`), also when a test fails.
- `QABZ_TEST_POSTGRES_DSN` is used only to reach the server (as an admin connection). No test connects to the database named in it for its work, and no test changes it.
- Inside the run database, the existing per-test isolation stays possible (for example the `postgrestest` schemas), but every object lives in the run database only.
- Every live test moves to this model: the task 003 tests (`live_test.go`, `reset()` is removed), `postgrestest`, `devdb` live tests, and the live tests of `entry/http`, `app` and `system/postgres`.

The rule is recorded as a new section of `docs/standards/PROJECT_SPECIFIC_CONVENTIONS.md`, so the `code-reviewer` agent checks it, and § 11 (coverage gate) is updated to describe the new DSN use.

Points for the design step:
- The unit of "one test run": Go runs each package as its own test binary, often in parallel. Options: one database per package run (`TestMain` in each package with live tests, through one shared helper in `postgrestest`), or one database for the whole `go test ./...` (a Make target that creates the database, passes its DSN, and drops it). Recommended: per package through `TestMain` and one helper, because it also works with a plain `go test <pkg>` and in parallel.
- A run that is killed (Ctrl-C, timeout) cannot drop its database. Decide how leftovers are found and removed (for example the helper drops `qabz_test_%` databases older than a fixed age at start, or a `make` target does it).
- The Postgres role that the DSN uses needs `CREATEDB`. Check the compose role, and document it.
- A guard: the helper refuses to run if the random database name equals the database named in the DSN or in `config.yml`.

## Definition of Done

- No test code creates, drops, truncates or resets anything outside the random run database. A search of the test code for `DROP`, `TRUNCATE`, `CREATE SCHEMA`, `CREATE DATABASE` shows only the shared helper and work inside the run database.
- `reset()` in `src/system/postgres/live_test.go` no longer touches the database in the DSN.
- Proof with the compose database: record the tables, schemas and `qabz_schema_migrations` row of the development database, run `go test -race -count=1 ./...` with `QABZ_TEST_POSTGRES_DSN` set, record them again. Pass: nothing changed, `app_hot_configs` and `qabz_schema_migrations` are still there, no `qabz_test_%` database and no `qabz_test_%` schema is left.
- A positive control: a test that drops a table in the DSN database (scratch change) is caught by the guard or by the proof above.
- The new conventions section is in `PROJECT_SPECIFIC_CONVENTIONS.md`, and § 11 is updated. The live tests still run (no skip) and the coverage gate still passes.
- Build, vet and tests (with `-race`) pass. The docs and the CHANGELOG are updated in the same commit.

## Decisions (operator, 2026-11-09)

The answers to "Points for the design step":
1. One test run is the whole `go test ./...`, through a Make target (`make test`). The target creates ONE database with a random name `qabz_test_<random hex>` on the server of an admin DSN, passes the DSN of that run database to all packages, runs the tests, and drops the database at the end (`DROP DATABASE ... WITH (FORCE)`), also when the tests fail or are interrupted where the shell can trap it. Exception (operator): a test may explicitly drop and recreate its OWN objects (or its own extra database) inside the run, but never anything in the development database.
2. Leftovers from a killed run are removed only by a Make target (`make test-db-clean`) that drops every `qabz_test_%` database on the server. Nothing removes them by itself.
3. Separation of DSNs (the rule that makes decision 1 safe): the run database DSN reaches the tests through its own environment variable, `QABZ_TEST_RUN_DSN`, that only the Make target sets. The admin DSN (server only) is a separate variable, `QABZ_TEST_ADMIN_DSN`, built from `config_generated.env` by the target. Without `QABZ_TEST_RUN_DSN` the live tests SKIP exactly as they skip today without a DSN. A shared helper refuses (FailNow) if the run database name does not start with `qabz_test_`, so no test can ever work in the development database. The existing per-test isolation (`postgrestest` schemas) stays, but inside the run database only.
4. `reset()` is removed from `src/system/postgres/live_test.go`. The task 003 tests then work in the run database; a test that needs an empty database drops and recreates its own objects inside the run database (the exception of item 1).
5. Check that the compose Postgres role has `CREATEDB` (the role is the database superuser in the official image, probably yes), and document what the target needs.
6. (operator, 2026-11-09, fix round 1) `GO_TEST_PKGS` is approved: the default `./...` is the whole run; it may name packages for QA scenarios and the conventions § 11 gate; each such run still gets its own random database.
7. (operator, 2026-11-09, fix round 2: "Clean roles, random pw") `testdb clean` (and so `make test-db-clean`) also drops every role whose name starts with `qabz_test_`, AFTER the `qabz_test_%` databases, with the same prefix rule (`qabz_test_` + letters, digits and `_`, `starts_with`, no `LIKE` wildcard), never a role without the prefix, one line `testdb: dropped role <name>` per role and a count. The password of a test login role is random for each run (the fixed special characters plus random hex from `crypto/rand`), so no usable password is in the repository.
8. (operator, 2026-11-09, fix round 3) "Nothing in the databases other than test_* databases must be touched." For this project: no test, no Make target and no `testdb` verb may create, change, drop, reassign, grant or revoke anything inside any database whose name does not start with `qabz_test_` (the development database `qabz`, `postgres`, the templates, any other). Reading catalogs (`pg_database`, `pg_roles`, `pg_shdepend` through the admin connection to `postgres`) is allowed; server-level `CREATE DATABASE` / `DROP DATABASE` of `qabz_test_` databases and `CREATE ROLE` / `DROP ROLE` of `qabz_test_` roles stay allowed. So `testdb clean` has no `REASSIGN OWNED` / `DROP OWNED`: a `qabz_test_` role that `DROP ROLE` cannot drop (2BP01) is kept, with `testdb: kept role <name>: it has objects or privileges in <db list> (not a test database); remove them by hand` (the list read from `pg_shdepend`). Exit code (operator default, the recommended option): when at least one role was kept, `clean` prints a final `testdb: <n> test role(s) kept` and exits 1 after it finished everything else, so `make test-db-clean` fails visibly; nothing kept: exit 0.

## Result (2026-11-09)

- `make test` (repo root): `go test $(GO_TEST_ARGS) $(GO_TEST_PKGS)` (defaults `-race -count=1 -cover` and `./...`) in ONE database `qabz_test_<16 hex>`. The target runs `make env`; `testdb admin-dsn <env file>` parses `config_generated.env` (the file is never sourced as shell) and prints the admin DSN (database `postgres`); `testdb name` gives the random name; the shell `EXIT` trap (`INT` → exit 130, `TERM` → exit 143) is set BEFORE `testdb create <name>`; the run DSN reaches the tests in `QABZ_TEST_RUN_DSN` only. `GO_TEST_PKGS` (decision 6) lets a QA scenario name fewer packages; the default is the whole run.
- `make test-db-clean`: drops every `qabz_test_%` database on the server, then every `qabz_test_` role (decision 7); a role that still has objects or privileges in a database that is not a test database is kept, named with that database, and the target exits 1 (decision 8). It never changes anything inside a database. Nothing else removes leftovers. It also drops the database of a `make test` that is still running: run it only when no `make test` is running (in `make help` and conventions § 14).
- New tool `src/system/postgres/postgrestest/testdb` (package `main`, tests only; Go driver, so no `psql` on the host): `admin-dsn <env file>`, `name`, `create <name>`, `drop <name>`, `clean` (the admin connection reads catalogs and runs only server-level `CREATE` / `DROP DATABASE` and `DROP ROLE` for `qabz_test_` names, decision 8). No DSN or password is ever an argument: `create`, `drop` and `clean` read the admin DSN from `QABZ_TEST_ADMIN_DSN` (set by the target for that one command). `create` and `drop` refuse a name that is not `qabz_test_` + letters, digits, `_` before they connect, and repeat a refused argument only when it has letters, digits and `_` only (a DSN given by mistake is never printed). `drop` of a name with no database does nothing and prints `testdb: no database <name>, nothing to drop` (the trap before `create`).
